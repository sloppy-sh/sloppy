## What it is for

Today one graph carries one tree: the genealogy, read as rows in [the outline reading](code:docs/images/reading-the-outline.jpg), with the Folgezettel addresses as its numbering. This note holds a proposal for more than that, made in the thread under the r/ContextEngineering post "Sloppy - Context/Drift-avoidance for humans and agents", and nothing here is decided. The commenter Doc1000 described a "graph to tree to cluster translation for discovery": a graph "still feels like search", while trees "let you start big/summarized and then progressively explore, or eliminate branches", so that "Agents/people end up with fewer things to hold in their context window at once." They added that "Every cluster up and down the hierarchy is a summary of some kind", that agents could label the clusters, and that "You can have more than one tree from the same graph based on different taxonomies, edges, scores."

The developer answered that Sloppy already does trees "loosely": "its a graph but with folgezettel", and "i just put a summary on the upper level of the tree".

## Still open

- Can several trees over one graph — one per taxonomy, or per set of tags — be derived rather than written, so that none of them becomes a second copy of the genealogy? The developer judged it "a thing to figure out on a technical level (in an automated system)".
- Who labels a cluster? The developer can "see humans maintain/do it longterm", and named "automating it into agents while preserving provenance and correctness" as "quite the task"; that question is [Agents writing documentation at scale, and who answers for it](sloppy:did:syr:z6MkofhdxKmE23ZUPQ65Lj7SynGSbLsL1ZNc81tgqQhg8h6X/01M5RYG00DHCCXDHGD91MEKA8C).
